# Nutrition estimates

For kitchen items without usable package nutrition, the Nutrition tab offers **Estimate nutrition info**. Google sign-in and an internet connection are required to request an estimate; anonymous manual inventory remains available. Optional details such as fat percentage and raw/cooked state improve specificity. The AI must state its assumptions. Its result is an approximate generic composition, not a verified database lookup or package label.

The preview uses the existing per-100, whole-package and custom-amount controls. Unknown nutrients remain absent rather than becoming zero. Saving requires explicit confirmation and commits to IndexedDB before showing Saved. Saved estimates work offline and sync with the private kitchen. Removing an estimate supports Undo. Existing package nutrition takes priority. Closing the item cancels the request; late responses cannot save inventory. A renamed food does not display an estimate for its previous name.

The existing JWT-protected `POST /v1/products/resolve` accepts `{ "kind": "nutrition", "name": "Ground beef", "details": "90% lean, raw" }`. Barcode requests are unchanged. Nutrition requests reject extra fields including model/provider overrides. Authentication, admission/suspension, request budgets, malformed-request protections, and the existing per-user/global AI budgets apply. Barcode classification and nutrition estimates share the AI allowance; this adds no separate paid budget.

The response is `{ estimate: NutritionEstimate | null }`. Null means no useful estimate (including nonfood). The object includes source `ai`, input name/details, timestamp, explicit assumptions, basis `g` or `ml`, and bounded per-100 nutrients. Calories use kcal, sodium uses mg, and other nutrients use grams. Optional unknown nutrients are null in the estimate; display conversion omits them. Strict structured output, size limits, timeouts, basic nutrient consistency checks and refusal/incomplete handling bound provider responses. This validation is not a factual nutrition guarantee. No automatic retry incurs another AI call.

The feature reuses the configured provider/model/reasoning/token budget and SSM secret. Provider access follows [OpenAI structured output guidance](https://developers.openai.com/api/docs/guides/structured-outputs). Credentials, provider error bodies, and kitchen identities are not sent to the UI or included in model input. Cache keys include a hashed account identity plus normalized input and model configuration; estimates are private and separate from the shared Open Food Facts catalog. Positive results cache for 30 days and unavailable-food results for one day. No Terraform apply or new AWS resource is needed.

Persistence adds optional `Food.nutritionEstimate` and the `food.nutrition` mutation (food ID, expected name, estimate or null). This command updates only estimate metadata, preserves lots and other edits, ignores missing/renamed foods, and never resurrects a deletion. Existing data needs no migration. Deploy the API before the frontend so it accepts the additive schema and mutation; older clients should update before editing foods with estimates.

Validation uses mocked provider/SSM/DynamoDB boundaries and production-build browser fixtures, including account changes, cancellation, offline persistence, explicit confirmation and package-label priority. These tests do not claim a live provider lookup or a physical Pixel keyboard/rendering test.
