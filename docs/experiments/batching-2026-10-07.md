# Food classification batch experiments — October 7, 2026

The previous 200-item result was twenty sequential ten-item calls. This experiment actually
sent 10, 40, 100 and 200 items **per provider request**. Larger batches help, but one 200-item
request did not finish within the existing fifteen-second deadline. Production batching,
model, reasoning settings, quotas, API body limit and worker cadence have not been changed.

## Method

Used the deployed `gpt-5.6-luna` model with `low` reasoning, strict structured output, `store:false`,
and the existing server-managed SSM key in memory. The CLI reads configuration from AWS but
cannot import cloud kitchen/access/product storage. It calls the provider through an isolated
experiment runner; it does not exercise the production route or DynamoDB worker.

The fixed corpus has 40 authored hard cases (branded foods, composites, unknowns, household items,
conflicting descriptions and instruction-like input) followed by 160 synthetic packages based on
registry identities. Most hard cases provide informative product descriptions. They are not
independently verified package labels, and this is not a names-only recognition benchmark.
Golden outcomes were written before responses and reviewed independently. Ten-item tests use the
first ten hard cases; forty-item tests use all hard cases; larger tests add synthetic controls.
Compare the same cohort when judging accuracy: total accuracy across these sizes is confounded
by the easier controls. The test set is small and not statistically representative of groceries.

Each size/format pair used identical inputs, with three deterministic shuffled repetitions and
interleaved condition order. Application classification caches were deliberately not consulted;
every attempt reached the provider. Provider prompt caching was retained and usage recorded.
The full format uses existing readable fields and review explanations. Compact uses numeric
registry indices, shorter field names and no free-text explanation; it retains explicit status
and preparation. Both enforce recognized/non-null and nonrecognized/null combinations. Decoders
validate count, index uniqueness, registry bounds and status consistency before scoring.
The compact prompt adds a numeric registry mapping, so this compares complete encodings, not
just output length. Registry indices are experiment-local and never persisted as identities.

To avoid confusing truncation with latency, experimental output caps scaled with size:
`min(12000, 512 + count × 60)` for full and `512 + count × 30` for compact. These caps are local
only. Separate 200-item tests retained the production 2,048-token cap. All requests retained the
15-second deadline. Reported timings cover provider HTTP request/response and decoding, excluding
SSM/configuration lookup and queue delay. No live worker throughput is claimed.

## Paired results

Medians/ranges below include successful responses only. Timeouts are separately counted and
censored at approximately 15 seconds; they are not treated as successful fifteen-second completions.
Three repetitions do not establish p95 latency or a reliability SLA.

| Items per call | Full completed | Full median (range)      | Compact completed | Compact median (range)   |
| -------------- | -------------- | ------------------------ | ----------------- | ------------------------ |
| 10             | 3/3            | 4.390 s (4.190–4.495)    | 3/3               | 3.465 s (1.962–3.574)    |
| 40             | 2/3            | 10.260 s (10.182–10.338) | 3/3               | 9.646 s (8.790–11.025)   |
| 100            | 0/3            | All timed out            | 3/3               | 14.091 s (13.775–14.631) |
| 200            | 0/3            | All timed out            | 0/3               | All timed out            |

At 200 items under the existing 2,048-token cap, both formats instead returned
`incomplete/max_output_tokens`: full in 13.452 seconds, compact in 14.454 seconds. Output capacity
and latency are distinct constraints. The equivalent production request body was 29,406 bytes,
also above the existing 16,384-byte route limit. Forty items occupied 5,296 bytes; 100 occupied
14,193 bytes with this fixture, leaving little room for richer metadata.

Among completed forty-item requests, full matched identity/status/preparation expectations on
79/80 hard-case observations; compact matched 109/120. Identity/status alone was 79/80 versus
118/120. At 100 items compact matched 299/300 identities but only 112/120 hard-case observations
including preparation. Most misses were conservative: cauliflower rice classified as a taxonomy
gap; dairy whole milk incorrectly treated as a gap; broth, soy sauce and cheddar left with unknown
preparation. Microwave brown rice and canned unsalted black beans were recognized correctly.
No false recognized identity was observed in the low-reasoning completed requests; this small
sample cannot establish safety, including allergy or dietary safety.

## Same 200-item workload

The full corpus was shuffled identically and split into five compact forty-item calls, first
sequentially and then with a maximum of two calls concurrently. All five calls completed in both
runs. These are one run per scheduling condition, not a statistically stable speedup estimate.

| Scheduling             | Total measured time | Identity/status correct | Hard cases including preparation | Estimated known token cost |
| ---------------------- | ------------------- | ----------------------- | -------------------------------- | -------------------------- |
| Sequential             | 36.558 s            | 199/200                 | 37/40                            | $0.00754                   |
| At most two concurrent | 23.804 s            | 199/200                 | 34/40                            | $0.00667                   |

The parallel run had 38,293/38,308 input tokens cached (99.96%), versus 32,495/38,308 (84.82%)
for sequential. Cache warmth, fixed run order and differing outputs confound an isolated concurrency
comparison; do not attribute the entire timing difference to parallelism. The different scores/costs
reflect nondeterministic responses and prompt-cache effects; concurrency does not inherently improve
classification or reduce tokens. Both runs abstained on cauliflower
rice, while several otherwise correct identities retained unknown preparation. One synthetic
fixture said “Canned mild green chiles” but supplied the registry's `plain` default; the model's
`canned` preparation is reasonable. The raw score retains this mismatch, but it must not be
presented as evidence of model error. Future corpus revisions should separate defaults from
observed product preparation.

Two additional compact twenty-item calls using the first twenty hard cases took 5.335 and
6.032 seconds, with all identities correct and 20/20 then 17/20 including preparation. This did
not test full-format twenty-item batching or the remaining twenty hard cases. An exploratory
`reasoning:none` forty-item call took 7.611 seconds but misclassified chopped cauliflower as
`cauliflower-head`, a distinction relevant to count quantities. Its 200-item counterpart still
timed out. Do not adopt disabled reasoning from these results.

## Budget, failures and reproducibility

The owner authorized continued experimentation after the local fifty-call limit had been reached.
The launcher explicitly sets a local-only daily allowance of 100, with accumulated counters
preserved. Ordinary local development still defaults to 50; production limits were not expanded.
Counters ended at 97: 47 additional attempts, comprising 40 usable experimental attempts plus
seven setup attempts. In the setup run, four completed responses were rejected by a harness bug
handling `error:null`, two timed out, and one was interrupted. These attempts remain counted;
their output/usage is unavailable and they are excluded from quality comparisons. Regression
coverage now accepts null envelope fields and checks compact index/identity validation.

The corrected 40 attempts produced 27 validated completions, eleven deadline failures and two
output-cap failures. Known usage across the returned responses estimates **$0.04784** using
[published Luna rates](https://developers.openai.com/api/docs/models/gpt-5.6-luna): $0.20/M input,
$0.02/M cached input and $1.20/M output tokens. This is **not the total billed cost**: usage for
timeouts and the seven setup attempts was not observed. The durable experiment ledger capped
corrected runs at forty reservations and 200,000 reserved output tokens; it recorded 136,916.
Each call is additionally bounded at 12,000 output tokens and 200 items. Counters and reports
were not reset or deleted. Provider schema restrictions follow the
[Structured Outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs).

Reproduce with `node scripts/experiments/run.mjs matrix`, `cap`, `workload 40 1`, `workload 40 2`,
or `followup`. Runs consume the persistent local quota and experiment ledger; they do not silently
start a new budget on restart. The ledger is in ignored `artifacts/local/experiment-budget-DATE.json`.
Source fixtures, contracts and scoring live in `api/experiments/`; generated bundles, response
records and summaries remain ignored under `artifacts/local/`.

The usable report files from this run are:

## Decision

The ten-item default was insufficiently justified. Moderate batches and at most two concurrent
calls are promising; waiting a minute between chunks is a worker scheduling limitation, not an AI
requirement. However, compact output still loses useful preparation information. One hundred has
too little deadline/body-size margin, and 200 fails the present constraints. Keep low reasoning.

Do not promote the experimental encoding or change production batch limits yet. The next focused
comparison should test 20–40 items with compact output that retains clear preparation semantics,
including the full hard-case set and inputs without helpful descriptions. Then choose bounded
parallelism, retry/splitting rules and token/item budgets together. A call-count quota alone becomes
less meaningful as batch size grows. Worker continuation should process remaining chunks promptly
after the grocery debounce, subject to durable leases and budgets, rather than imposing another
minute per chunk. These conclusions are preparation for an implementation decision, not deployment.

## Subsequent owner decision: 25 items

The owner selected 25 items as the initial implementation limit, deferring further optimization.
The shared request/response schemas, worker and local test client now use that limit. The full
result format, configured low reasoning, 2,048-token cap, fifteen-second deadline and production
AI quotas remain unchanged. Shared batch selection also respects the existing 16,384-byte UTF-8
request ceiling, retaining complete metadata and queued remainder. Worker cadence is unchanged:
one kitchen batch per invocation on the minute schedule, with remaining work eligible after a
minute; concurrency and immediate continuation remain deferred.

A fresh local API request with 25 distinct ordinary/branded product fixtures completed in
9.114 seconds with no cached results or failures. Cooked brown rice and canned unsalted black
beans were recognized; composite meals, unknown names, nonfood and missing taxonomy entries
remained explicit. An identical repeat reused all 25 persisted results in 21 milliseconds. This
is a smoke test, not a latency or accuracy guarantee. See local testing notes for browser checks.
